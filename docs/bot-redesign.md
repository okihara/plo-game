# Bot AI 再設計案（0からの設計し直し）

現行 Bot（`server/src/shared/logic/ai/`）はルールツリー + パラメータ乱数方式で、
`/morning-bot-improve` によるパラメータ微調整を重ねても対人間 -20〜-40 BB/100 が続いている
（`docs/bot-tuning-log.md` 参照）。本ドキュメントは「なぜエクスプロイトされるのか」の構造分析と、
再設計のアーキテクチャ・移行計画をまとめる。

## 1. 現行設計がエクスプロイトされる構造的理由

個々のパラメータ値ではなく、**設計そのもの**に起因する穴が 6 つある。

### 1-1. ベットサイズを見ずにフォールドする分岐がある

`postflopStrategy.ts` の foldToCbet 分岐（L49-57）は、相手のベットが
ポットの 10% でも 100% でも同じ確率でフォールドする。
→ **ミニベット連打だけで利益が出る**。人間側は 1BB のベットでポットを大量に拾える。

### 1-2. フォールド頻度が MDF（最低防御頻度）を大幅に超えている

リバーのワンペアは基礎フォールド率 80%（クランプ下限 65%）、ツーペアは基礎 65%（下限 40%）。
合成すると、Bot がリバーで「ナッツ級以外」を持つ全ケースで 60-90% フォールドする。
→ **リバーは何も持っていなくてもベットすれば勝ち**。ブラフの採算ラインである
「ポットベットなら 50% 降りれば十分」を常に大幅に超えている。
プリフロップも同様: 4bet には AAxx 以外 100% フォールド（`preflopStrategy.ts` L56-59）、
3bet には構造が悪ければ最低 55% フォールド。**3bet/4bet ブラフが打ち放題**。

### 1-3. 「絶対ハンド強度」で考え、レンジ・ボード文脈がない

`madeHandRank`（ツーペア=3、セット=4…）と `madeHandRankToEquity` の固定テーブル
（ツーペア=50% など）が判断の主軸。T987 モノトーンのセットと K72 レインボーのセットが
ほぼ同じ扱いになる。nutRank による補正はリバーのみ。
→ 人間は「このボードで Bot のこのアクション＝この強度帯」と読み切れる。

### 1-4. アクションに一貫した計画がなく、ノードごとに独立サイコロ

各判断が独立した `Math.random()` なので、「フロップでベット → ターンで理由なく諦める」
「同一ハンド内で強気と弱気が混在」というラインになる。
`shouldBarrel` のバレル率は実質 30-60% 程度で、**フロップ C ベットにコールしてターンの
チェックを待つだけ（フロート）で勝てる**。ドンク 40%/20%/15% のような固定頻度も
逆算されると情報リークになる。

### 1-5. ベットサイズがハンドクラスと相関している（サイズテル）

`betSizing.ts` はハンドクラス別に別関数でサイズを決める
（バリュー 75-100%、ブラフ 50-65%、ミディアム 25-40%）。±5% の乱数では隠せない。
→ **サイズを見れば手が読める**。特に「小さいベット＝ミディアム/ポットコントロール」は
レイズで即座に降ろせる。

### 1-6. 適応がない（同じエクスプロイトが永久に効く）

`SimpleOpponentModel` は接続ごとのオンメモリで、ハンドをまたぐ蓄積も
プレイヤー個人への対応もほぼ機能していない（fold 率推定が probe 判断に薄く使われる程度）。
→ 一度見つけた穴を**同じプレイヤーが何百ハンドでも搾取し続けられる**。
現在の対策サイクルは「翌朝人間が集計して ±10% 調整」のみで、フィードバックループが 1 日単位。

### 補足: パラメータ調整で直らない理由

`personalities.ts` の vpip/foldToRiverBet 等をどう動かしても、上記 1-1〜1-5 は
「どの値でも搾取可能な構造」なので解消しない。5/15 に 3 パーソナリティを
ほぼ同一値に収束させた事実自体が、パラメータ空間に解がないことの傍証。

## 2. 再設計の原則

1. **すべての判断はエクイティ vs 価格（ポットオッズ）で行う** — サイズを見ないフォールド分岐を設計上作れなくする。
2. **相手レンジを明示的に持つ** — 絶対ハンド強度ではなく「相手の継続レンジに対する勝率」で判断。
3. **防御頻度に下限を敷く（MDF ガード）** — どのノードでも「ベットサイズから計算される必要防御頻度」を下回るフォールドをしない。ブラフキャッチはブロッカーで選ぶ。
4. **ハンド単位の一貫した計画** — ストリート冒頭に「バリュー/セミブラフ/ブラフ/ショーダウン/降り」の役割を割り当て、ハンド内で seed 固定した乱数で一貫させる。
5. **サイズはレンジで決め、ハンドで決めない** — サイズ候補を少数（33/66/100%）に離散化し、各サイズにバリューとブラフを混ぜる。
6. **適応は自動で、ただし有界に** — 対戦者ごとの傾向を DB に永続化し、逸脱（過剰ブラフ等）に対してのみ閾値を有界にシフト。逆エクスプロイトされない範囲に制限。
7. **デプロイ前に「エクスプロイターとの対戦」で計測する** — 弱点はレビューではなくシミュレーションで検出する。

## 3. 新アーキテクチャ

```
server/src/shared/logic/ai2/          ← 新エンジン（旧 ai/ と並存、strategyRegistry で切替）
├── engine/
│   ├── decisionEngine.ts             ← エントリ。候補アクションの EV を比較して選択
│   ├── evCalculator.ts               ← EV(fold/call/bet_s) の計算
│   └── actionPlan.ts                 ← ハンド単位の役割割り当て（seed 付き乱数）
├── range/
│   ├── rangeModel.ts                 ← 相手レンジ（重み付きコンボ集合）の生成・更新
│   ├── rangeFilter.ts                ← アクション履歴によるベイズ更新（緩い条件付け）
│   └── populationPriors.ts           ← 人間集団の事前分布（VPIP/ベットサイズ別強度）
├── equity/
│   ├── monteCarloEquity.ts           ← 対レンジ勝率のサンプリング推定（予算内）
│   └── equityCache.ts                ← ストリート内キャッシュ
├── defense/
│   ├── mdfGuard.ts                   ← フォールド頻度の下限保証・ブラフキャッチ選択
│   └── blockerSelector.ts            ← 既存 blockerAnalysis を流用
├── sizing/
│   └── rangeSizing.ts                ← サイズ離散化・バリュー/ブラフ混合比の管理
├── adapt/
│   ├── opponentProfile.ts            ← 対戦者プロファイル（DB 永続化、Prisma）
│   └── exploitDetector.ts            ← 過剰ブラフ/過剰フォールド等の検出と有界補正
└── sim/
    ├── simulator.ts                  ← オフライン高速対戦（gameEngine 再利用）
    ├── exploiters/                   ← ミニベッター/リバー爆撃/フロート等の敵エージェント
    └── report.ts                     ← BB/100・被エクスプロイト額のレポート
```

### 意思決定フロー（1 アクション）

1. `rangeModel` が各相手の現在レンジを返す（プリフロップ参加サイズ・ライン・
   `opponentProfile` の統計で重み付け）。
2. `monteCarloEquity` が自ハンド vs レンジの勝率を推定
   （フロップ以降、~200 サンプル × ランアウト。既存 `evaluatePLOHand` を利用。
   予算超過時は worker_threads へ — allin EV と同じ基盤 [[allin-ev-offload]]）。
3. `evCalculator` が候補（fold / call / サイズ別 bet-raise）の EV を計算。
   フォールドエクイティは相手プロファイルの「サイズ別継続率」から。
4. `mdfGuard` が「対ベットのフォールド率が必要防御頻度を超えていないか」を検査し、
   超過しそうならブロッカー最良の手をコールに回す。
5. `actionPlan` のハンド内 seed で EV 近接候補を混合（softmax）。
   → 乱数はここ 1 箇所だけ。EV 差が大きければブレない。
6. パーソナリティは最終段の薄い係数（アグレッション・VPIP オフセット）としてのみ適用。

### 旧 ai/ から流用するもの

- `preflopEquity`（packages/shared）— プリフロップスコアは実績があるので継続使用
- `nutsAnalysis` / `blockerAnalysis` / `boardAnalysis` — ボード・ブロッカー解析は良質
- `strategyRegistry` — variant 切替の枠組み。PLO/PLO5 のみ新エンジン、他 variant は旧のまま

## 4. 移行計画

### Phase 0: 実データでエクスプロイト実態を計測（✅ 2026-07-31 実施済み）

スクリプト: `server/scripts/bot-exploit-analysis.ts`（`--prod --days 7`）。
直近 7 日・リング PLO4・人間 Bot 同席 30,185 ハンドの結果:

- 対象ハンド内損益: **Bot -102,856 / 人間 +51,537**
- **リバー過剰フォールドが最大の穴**: 人間のリバーベットに対しサイズ不問で 55〜69% フォールド。
  ≤25% ポットの超小型ベットにも 54.7% 降りる（ブラフ採算ライン 20%）。
  実測の人間リバーベットのブラフ率（ワンペア以下）は 18.9% だが、
  ブラフに 69.7% フォールドしつつ、ストレート以上のバリューには 22.8% コールしており両方向で損。
- **vs3bet フォールド 79.6% / vs4bet+ フォールド 79.7%**（3bet ブラフ採算ライン約 67%）。
  4bet+ への Bot のレイズは 0.0%。
- **フロップ/ターンは逆に降りなさすぎ**: フォールド 3〜16%、レイズ 19〜35%。
  「序盤にポットを膨らませてリバーで投降」の最悪の組み合わせ。
- 当初仮説の「フロップミニベット搾取」（1-1）は実際には起きていない
  （フロップ ≤25% ベットへのフォールド 3.1%）。foldToCbet 分岐の設計欠陥自体は残るが優先度低。
- フロート（Bot flop-cbet → turn check → 人間 bet）への降りは 9.6% で問題なし。
- 上位搾取者の例: 269 BB/100（リバーベットの 39% がワンペア以下）、
  91 BB/100 × 3,164 ハンド（3bet 146 回）など、リバー爆撃型と 3bet 型が上位。

### Phase 1: 即効パッチ（旧エンジンのまま・1 日）

Phase 0 の実測に基づき優先順位を変更。構造は変えず 2 箇所だけ止血:
1. **リバーのフォールド率をベットサイズ主導に**: サイズ係数を掛け、クランプ上限を引き下げ
   （ワンペアも小型ベットには防御、ツーペア+の過剰フォールドを緩和）
2. **3bet/4bet へのフォールド率に上限**: 4bet に AAxx 以外全降りをやめ、
   良構造プレミアムはコール継続。3bet への最低強度・フォールド率を引き下げ
（フロップミニベット対応は実害が出ていないため Phase 2 の新エンジンに委ねる）

### Phase 2: 新エンジン骨格 + シミュレータ（🚧 2026-07-31 進行中）

- ✅ `ai2/sim/` シミュレータ + エクスプロイター 5 種（RiverBomber / 3BetBluffer /
  MinBetter / Floater / Nit 対照群）。`npx tsx scripts/bot-sim.ts` で再現可能。
- ✅ ベースライン計測（各 20,000 ハンド, seed=1, エクスプロイターの BB/100）:

| エクスプロイター | Phase 1 前 | Phase 1 後(現行) | 解釈 |
|---|---|---|---|
| RiverBomber | -73.2 | -154.6 | リバー防御強化が効いた |
| 3BetBluffer | -150.0 | -274.6 | 3bet/4bet 防御強化が効いた |
| MinBetter | **+50.2** | -1.9 | 小型ベット搾取が消えた |
| Floater | -52.9 | -248.0 | リバーコール増でスタブが払う側に |
| Nit (対照) | +59.0 | **+67.7** | **残る最大の穴: バリューへの払いすぎ** |

- 検証: シミュレータは Phase 0 で実測した搾取（ミニベット・リバー爆撃・3bet）の
  方向を正しく再現し、PR #203 の効果も検出できた。
- **残る本丸は「タイトに待つだけの相手に +60 BB/100 払う」過剰コール**
  （Phase 0 のフロップ/ターン フォールド 3〜16% と整合）。これが新エンジンの主眼。
- ✅ 新エンジン v1 (`ai2/engine/` + `PLOStrategy2`): 対レンジ・モンテカルロエクイティ
  + EV 比較 + エクイティ実現率割引 + ハンド内シード softmax。プリフロップは旧
  （Phase 1 パッチ済み）を再利用。
- 合格基準: 全 exploiter に対して 0 BB/100 以下（Nit 含む）、新旧直接対決で v2 側が正。

### Phase 3: 本番 A/B 投入（1 週）

- strategyRegistry で Bot の一部（例: 3 分の 1）を新エンジンに割り当て
- `/morning-bot-improve` の集計を新旧比較レポートに拡張
- 対人間 BB/100 で新旧比較 → 良ければ全量切替

### Phase 4: 適応層（その後）

- `opponentProfile` の DB 永続化（Prisma に BotOpponentProfile テーブル追加。
  本番 DDL なので実施タイミングは事前確認 [[feedback_prod_db_timing]]）
- exploitDetector による有界な自動カウンター調整

## 5. 評価とガードレール

- **オフライン**: sim/ の exploiter スイートを CI 的に回し、変更ごとに被搾取額を計測
- **本番**: 既存の日次集計（BB/100、WSD、ポジション別）+ 新規に
  「対ベットサイズ帯別フォールド率」「リバーコール時勝率」をモニタ
- **CPU 予算**: 1 決定あたり同期 20ms 以内を目標。超える場合は worker_threads
  （tsx 環境の worker 読み込みは [[tsx-worker-threads]] の方式）
- パーソナリティ 3 種の枠組み・Bot の見た目/名前は変更しない（プロダクト仕様は不変）

## 6. 決定事項（2026-07-31 ユーザー確認済み）

1. **目標水準**: 「搾取されない」レベル（対人間 -5〜0 BB/100 目安）。勝ちに行くことは目的にしない。
2. **適応の粒度**: **集団適応のみ**。プレイヤー個人へのカウンター適応はやらない
   （opponentProfile は集団統計＝人間全体の傾向の保持に限定する）。
3. **対象 variant**: **リング PLO4 のみ**。PLO5・トーナメント・他 variant は旧エンジンのまま。
